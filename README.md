# 🌙 Mood & Symptom Tracker

A small web app for logging how you feel, several times a day. Mood is the centerpiece: instead of a single 1–5 scale, you build up your own vocabulary of feelings (calm, grateful, anxious, …) and log check-ins against it. Physical symptoms (headache, fatigue, …) are tracked in a separate log on their own timeline.

It consists of a JSON REST API (Express + SQLite) with user accounts, and a plain HTML/JavaScript frontend that uses that API. Every user has their own private moods, symptoms and entries.

## Features

- **Accounts**: register and log in with email and password; passwords are stored only as salted scrypt hashes
- **Private data**: each user only ever sees and changes their own moods, symptoms and entries
- **Mood check-ins**: pick a mood, optionally rate how you feel (1–5) and note what triggered it
- **Symptom log**: pick a symptom, optionally rate its intensity (1–5) and add a trigger
- **Your own vocabulary**: add new moods and symptoms at any time; duplicates are rejected regardless of case or spacing
- **Recent entries** for both logs, newest first, with delete
- **Validation in two layers**: the API validates every request, and the database enforces the same rules with constraints
- **Automated API tests** with Node's built-in test runner

## Tech stack

| Part | Technology |
|---|---|
| Server | [Node.js](https://nodejs.org/) + [Express 5](https://expressjs.com/) |
| Database | SQLite via Node's built-in [`node:sqlite`](https://nodejs.org/api/sqlite.html), plain SQL with parameterized queries (no ORM) |
| Authentication | Server-side sessions in SQLite, `HttpOnly` session cookie ([cookie-parser](https://github.com/expressjs/cookie-parser)), password hashing with `scrypt` from `node:crypto` |
| Frontend | HTML + JavaScript modules, no framework, served by Express |
| Styling | [Tailwind CSS v4](https://tailwindcss.com/) (CLI build) |
| Tests | [`node:test`](https://nodejs.org/api/test.html) + `node:assert`, against an in-memory database |

## Getting started

**Requirements:** Node.js 22.13 or newer (developed on Node 24), because `node:sqlite` is built into Node from that version on.

```sh
git clone https://github.com/shiorissk/mood-tracker.git
cd mood-tracker
npm install
```

**Run in development** (two terminals):

```sh
npm run dev         # API + frontend on http://localhost:3000, restarts on file changes
npm run watch:css   # rebuilds the Tailwind CSS on every save
```

**Run normally:**

```sh
npm start           # builds the CSS first, then starts the server
```

Open http://localhost:3000 and create an account. The database file and its tables are created automatically on first start.

Optional settings go in a `.env` file in the project root:

| Variable | Default | Description |
|---|---|---|
| `PORT` | `3000` | Port the server listens on |
| `DB_PATH` | `mood.db` | Path of the SQLite database file (relative to where the server is started) |

## API reference

Base URL: `http://localhost:3000`

### Conventions

- Request and response bodies are JSON. Send `Content-Type: application/json` with every request that has a body.
- **Authentication uses a session cookie.** `POST /auth/login` sets a `sessionId` cookie; send it with every later request. Browsers do this automatically; with curl use `-c` to save it and `-b` to send it (see the [examples](#examples-with-curl)).
- **Everything except `/health` and `/auth/*` requires a login**, and only ever works on the logged-in user's own data. Another user's items behave as if they don't exist (`404`).
- **Lists are wrapped** in an object (`{ "moods": [...] }`); **single items are returned directly**.
- Timestamps are ISO 8601 strings in UTC, e.g. `"2026-10-26T14:16:10.427Z"`.
- Names of moods and symptoms are stored **trimmed and lowercase**.
- Every error has the same shape:

  ```json
  { "error": "feelingScore must be an integer between 1-5" }
  ```

| Status | Meaning |
|---|---|
| `200` | OK |
| `201` | Created; the body is the new item |
| `204` | Done; no body (delete, logout) |
| `400` | Invalid input, including malformed JSON |
| `401` | Not logged in, session expired, or wrong email/password |
| `404` | No item with that id (for this user), or unknown route |
| `409` | That email, mood or symptom already exists |
| `500` | Unexpected server error (details are only logged on the server) |

### Health

#### `GET /health`

```json
{ "status": "ok" }
```

### Authentication

#### `POST /auth/register`

```json
{ "email": "you@example.com", "password": "at least 8 characters" }
```

| Field | Rules |
|---|---|
| `email` | Required string containing `@`. Trimmed; compared case-insensitively. |
| `password` | Required string, at least 8 characters. Only a salted hash is stored. |

**201** with the new user (never the password or its hash):

```json
{ "id": 1, "email": "you@example.com" }
```

**400** if the email or password is invalid. **409** if the email is already registered (`"YOU@example.com"` counts as a duplicate). Registering does **not** log you in; call `/auth/login` next.

#### `POST /auth/login`

```json
{ "email": "you@example.com", "password": "your password" }
```

**200** with `{ "id": 1, "email": "you@example.com" }` and a session cookie:

```
Set-Cookie: sessionId=…; Max-Age=604800; Path=/; HttpOnly; SameSite=Lax
```

Sessions last **7 days**. **400** if `email` or `password` isn't a string. **401** `"Invalid email or password"`, with the same message for an unknown email and a wrong password, so the API doesn't reveal which emails are registered.

#### `POST /auth/logout`

Deletes the session on the server and clears the cookie. **204** with no body, also when you weren't logged in. The old session id stops working immediately.

#### `GET /auth/me`

**200** with the logged-in user, **401** if not logged in. The frontend uses this on page load to decide between the login form and the app.

```json
{ "id": 1, "email": "you@example.com" }
```

### Moods and symptoms

`/moods` and `/symptoms` work the same way. Each user has their own list.

#### `GET /moods`

```json
{
  "moods": [
    { "id": 1, "name": "calm", "userId": 1 },
    { "id": 2, "name": "grateful", "userId": 1 }
  ]
}
```

`GET /symptoms` returns `{ "symptoms": [...] }`.

#### `POST /moods`

```json
{ "name": "Anxious" }
```

| Field | Rules |
|---|---|
| `name` | Required, non-empty string. Trimmed and lowercased before saving. |

**201** with the new item:

```json
{ "id": 3, "name": "anxious", "userId": 1 }
```

**400** if `name` is missing, empty or not a string. **409** if you already have a mood with that name (`" CALM "` counts as a duplicate of `"calm"`). Two different users can both have `"calm"`.

### Mood entries

A mood entry is one check-in. Every response includes `moodName`, so clients don't need a separate lookup.

```json
{
  "id": 7,
  "moodId": 1,
  "moodName": "calm",
  "createdAt": "2026-10-26T14:16:10.427Z",
  "feelingScore": 4,
  "trigger": "walk outside"
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | integer | Set by the database |
| `moodId` | integer | Required; must be the `id` of one of **your** moods |
| `moodName` | string | Read-only, joined from the mood |
| `createdAt` | string | Read-only, set by the database |
| `feelingScore` | integer or `null` | Optional, 1–5, **5 = feels good** |
| `trigger` | string or `null` | Optional; trimmed, an empty string is stored as `null` |

#### `GET /mood-entries`

```json
{ "moodEntries": [ { "id": 1, "moodId": 2, "moodName": "grateful", ... } ] }
```

Your entries only, sorted by `id`, oldest first.

#### `GET /mood-entries/:id`

**200** with the entry, **404** if it doesn't exist or belongs to another user.

#### `POST /mood-entries`

```json
{ "moodId": 1, "feelingScore": 4, "trigger": "walk outside" }
```

Only `moodId` is required; `feelingScore` and `trigger` can be left out or sent as `null`.

**201** with the full entry, including `id`, `moodName` and `createdAt`. **400** if `moodId` is missing, not an integer (`"1"` is rejected) or not one of your moods; if `feelingScore` isn't an integer from 1 to 5; or if `trigger` isn't a string.

#### `PATCH /mood-entries/:id`

Send only the fields you want to change:

```json
{ "feelingScore": 5 }
```

- Fields you leave out stay as they are; `{}` changes nothing.
- `null` removes an optional value: `{ "trigger": null }` clears the trigger.
- `moodId` can be changed (to another of your moods) but not removed: `{ "moodId": null }` is rejected.
- `id` and `createdAt` can't be changed.
- The update is all-or-nothing: if any field is invalid, nothing is changed.

**200** with the updated entry, **400** for invalid fields (same rules as `POST`), **404** if the entry doesn't exist or belongs to another user.

#### `DELETE /mood-entries/:id`

**204** with no body, **404** if the entry doesn't exist or belongs to another user.

### Symptom entries

`/symptom-entries` works exactly like `/mood-entries`, with these field names:

| Mood entries | Symptom entries | Notes |
|---|---|---|
| `moodId` | `symptomId` | Must be the `id` of one of your symptoms |
| `moodName` | `symptomName` | |
| `feelingScore` | `intensity` | 1–5, **5 = most severe** |

The list endpoint returns `{ "symptomEntries": [...] }`.

### Examples with curl

```sh
# create an account, then log in and save the session cookie to cookies.txt
curl -X POST localhost:3000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email": "you@example.com", "password": "secret123"}'

curl -c cookies.txt -X POST localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "you@example.com", "password": "secret123"}'

# add a mood, then log a check-in with it (-b sends the cookie)
curl -b cookies.txt -X POST localhost:3000/moods \
  -H "Content-Type: application/json" \
  -d '{"name": "calm"}'

curl -b cookies.txt -X POST localhost:3000/mood-entries \
  -H "Content-Type: application/json" \
  -d '{"moodId": 1, "feelingScore": 4, "trigger": "walk outside"}'

# change the score, then delete the check-in
curl -b cookies.txt -X PATCH localhost:3000/mood-entries/1 \
  -H "Content-Type: application/json" \
  -d '{"feelingScore": 5}'

curl -b cookies.txt -X DELETE localhost:3000/mood-entries/1

# log out: the saved cookie stops working
curl -b cookies.txt -X POST localhost:3000/auth/logout
```

`cookies.txt` contains a real session id, so it is git-ignored.

## Data model

Users own everything else. Each data table has a `userId` foreign key; entries additionally point to one mood or symptom. The full definitions are in [`src/db/schema.sql`](src/db/schema.sql).

```
User ──< Session
  │
  ├──< Mood ──< MoodEntry          (MoodEntry.userId → User)
  └──< Symptom ──< SymptomEntry    (SymptomEntry.userId → User)
```

| Table | Columns |
|---|---|
| `User` | `id` (primary key), `email` (unique, case-insensitive), `passwordHash` (`salt:hash` in hex), `createdAt` |
| `Session` | `id` (random 64-character hex string, primary key), `userId` → `User.id`, `expiresAt` |
| `Mood` | `id`, `name` (case-insensitive), `userId` → `User.id`; `UNIQUE (userId, name)` |
| `MoodEntry` | `id`, `moodId` → `Mood.id`, `createdAt`, `feelingScore` (1–5 or NULL), `trigger`, `userId` → `User.id` |
| `Symptom` | `id`, `name` (case-insensitive), `userId` → `User.id`; `UNIQUE (userId, name)` |
| `SymptomEntry` | `id`, `symptomId` → `Symptom.id`, `createdAt`, `intensity` (1–5 or NULL), `trigger`, `userId` → `User.id` |

All tables are `STRICT` (column types are enforced), integer ids use `AUTOINCREMENT` (never reused), and foreign keys are enforced with `PRAGMA foreign_keys = ON`.

## Testing

```sh
npm test
```

Each test file starts the app on a random free port with its own empty in-memory database (`DB_PATH=:memory:`), registers and logs in a test user, and sends real HTTP requests with `fetch`. Nothing touches your `mood.db`.

The tests cover:

- **Every endpoint's happy path and validation** (one file per router), including partial and all-or-nothing `PATCH`
- **Auth**: register (no password hash in the response, duplicate emails, invalid input), login (same error for unknown email and wrong password), `/auth/me`, and logout invalidating the session
- **Protection**: every data router answers `401` without a cookie
- **Isolation**: a second user can't read, change, delete or list the first user's entries

## Design decisions

- **Lookup tables instead of free text or enums**, so moods and symptoms can be added at runtime, typos can't create near-duplicates, and renaming happens in one place.
- **Moods and symptoms are separate logs** on their own timelines, not mixed into one entry.
- **One mood per check-in**, kept simple on purpose; several check-ins a day are expected.
- **The scales point in opposite directions:** `feelingScore` 5 = good, `intensity` 5 = bad. The frontend colours them accordingly.
- **Rules are enforced twice:** the API validates types and ranges and returns clear `400` messages; the database repeats the important rules (`NOT NULL`, `UNIQUE`, `CHECK`, foreign keys) as a safety net.
- **`trigger` instead of a general note**, because it's more useful for later questions like "which triggers come up most?". A `note` column can be added later.
- **Raw SQL instead of an ORM**, to keep every query visible.
- **The frontend only talks to the API**, never to the database, so all validation happens in one place.
- **Sessions instead of JWTs.** The frontend is served from the same origin, so a cookie is the natural fit. A session row in the database can be deleted, so logout takes effect immediately, which a stateless JWT can't do before it expires. The cookie is `HttpOnly` (page scripts can't read it) and `SameSite=Lax` (not sent on requests started by other sites).
- **Ownership instead of roles.** Every user owns their own data and there is no admin role, so permissions come down to one rule: every query is filtered by the logged-in user's id. Other users' items answer `404` rather than `403`, so ids reveal nothing about other users.
- **One error message for unknown email and wrong password**, so login can't be used to find out who has an account.
- **Passwords hashed with `scrypt`** (built into Node, deliberately slow) with a random salt per user, compared with `timingSafeEqual`.
